# Feature-first roadmap

Complete reusable game features before ordinary content authoring. Use only a few test things to prove each acceptance loop. The [design work plan](../design/WORK_PLAN.md) supplies detailed dependency contracts; the [eight-pass plan](eight-pass-release-plan.md) groups release work. Neither makes unimplemented systems complete.

## P1 foundation checkpoints

| Checkpoint | Current state | Next acceptance work |
|---|---|---|
| Design-to-implementation registry | Implemented scoped overlay and dependency plan | Keep requirement evidence precise; assess unreviewed sections as their domains are built |
| Field lifetimes and Ascension | Migration 030, preview/confirm and small campaign/new-life/replay proof | Extend the manifest and carry/reset/archive proofs whenever a domain adds state |
| Shared rules, clocks and prerequisites | Migration 031; two domain adapters reuse checks, prerequisites, effects and rewards | Integrate later feature domains without copied math; deliberate staging rehearsal and enablement remain separate |
| Documentation and Follybound pages | This pass reconciles names, evidence and navigation | Keep implementation, plans and activation distinguishable at every later checkpoint |

## 1. Complete progression and run setup

Finish training/practice with journaled meaningful check evidence; rank and capability changes; safe respec; species/background and special-start rules; and account Mastery/Legacy. Resolve remaining initiation, Ascension eligibility/rewards and mode/path contracts from their owning design entries. Use current class/XP journals, `src/rules/` and field lifetimes, not parallel progression state.

Finish when a small life proves earned growth, legal choices and respec, campaign completion, preview, exact carryover and a second build; duplicated, stale, revoked and interrupted actions reconcile. Noncombat progress must award a principal obstacle budget once, with no alternative-approach double claim. Breaking content changes need explicit compatibility contracts.

## 2. Quests, dialogue, travel and world consequences

Build validated quest/objective graphs and reward identities; NPC memory/dialogue choices; route/travel costs and visibility; faction/world consequence scope; and fail-forward branches. Reuse shared prerequisite/check/cost/reward/effect services. A generic interaction adapter alone does not finish these workflows.

Finish when combat and a peaceful approach solve the same small objective, claim its principal reward once, reveal only known choices, and preserve/reset the correct consequences across Ascension. Test invalid graphs, dead ends, retries, foreign ownership, conflicting choices and concurrent claims.

## 3. Items and crafting lifecycle

Extend routine recipes into profession/station eligibility, quality and capacity; delayed work and recovery; durability/repair; upgrades and commissions. Integrate item protections and binding with every destructive action and custody transition.

Finish when a tiny gather → process → craft → equip → wear/repair → store/commission loop conserves inputs, outputs and currency under retries, interruption and Ascension. Synthetic recipes come before production catalogs.

## 4. Daily, rest and Home systems

Configure authored Turn/banking policy, consumption, rest recovery, Home production and due-work settlement. Connect owned systems to durable rollover/scheduler and shared clocks. Never invent real-time tactical pressure; only explicit permitted event/shared-instance windows use wall time.

Finish when downtime and repeated jobs produce exactly one entitlement, overcap and carryover behavior is correct, combat postponement is safe, and rest/effect expiration reconciles across boundaries and new lives.

## 5. Shared launch features and client workflows

Decide which guild, market, trade, event, companion/social, multiplayer, raid and PvP systems ship. Build permission and claim/custody contracts for the included systems; record explicit deferrals. Consent-based shared tactical combat is a starting point, not completion of this group.

Finish each included feature with a minimal end-to-end scenario, ownership/content discovery checks, contention tests, disconnect recovery, emergency-disable behavior and exactly-once costs/rewards. Add understandable browser workflows and explanations alongside each feature; server-only APIs do not satisfy player acceptance.

## 6. Administration and production safety

Complete staff authority, repair through compensating history, verified support/contact, export/redaction and retention. Establish independent recovery targets, PITR if required, independent-machine restoration, alert delivery, representative migration rehearsals and capacity/failure drills. Keep live/staging credentials and data separate.

Finish when the [release gates](release-readiness.md) have dated evidence for the exact release/configuration. Source tests and a same-machine restore do not replace those gates.

## 7. Production content and launch verification

Only after each needed framework and authoring workflow passes, author the actual world, campaign, class/item/recipe catalogs and balance data. Validate references, reachability, discovery, reward budgets, lifetimes and release compatibility. Expand representative content and playtest volumes; verify accessibility, onboarding, recovery and moderation. Seal and rehearse the release, review staging, then explicitly approve activation.

At every step update the implementation guide, API/migration guide, field manifest, registry evidence and public copy when their claims change. Do not silently rewrite historical content or promote test fixtures into launch promises.
